# Aqua Luna · 시스템 개발 작업 목록

작성: 2026-10-05  
근거: [연애 시뮬레이션 조사 보고서](../reports/DATING_SIM_RESEARCH.md)  
상태: **제안·개발 준비 문서**. 이 문서 작성으로 게임 기능이 추가된 것은 아닙니다.

후속 구현: 시간대 배경, 출발 시간 앨범 기록, 의상별 지원 표정과 갤러리는 `src/data.js`/`app.js`에 반영했습니다. 이미지 명세는 [시간대 확장 기록](ART_DAYTIME_EXPANSION.md)에 있습니다. 별도 `asset-manifest.js`는 생성하지 않고 `LunaData.assetPaths`에서 34장 목록을 도출해 브라우저로 검사했습니다. 대화 세션·이벤트 큐·관계 단계는 아래 계획 상태이며, [스토리 초안](../reports/STORY_SCENARIO_REVIEW_v0.1.md)은 사용자 확인 대기입니다.

## 개발 원칙

현재의 설치 없는 HTML/JavaScript 구조를 유지합니다. 텍스트·메뉴 중심 게임에 맞춰 상태 전이와 화면을 분리하며, 엔진 교체를 이번 목표에 포함하지 않습니다. Game Studio의 web-game-foundations 지침 중 상태·표시·저장 분리를 적용합니다.

일하기 → 구매 → 수련에게 직접 착용 → 데이트 → 기록이라는 기존 사용자 요구를 보존합니다. 검은 스타킹·살색 스타킹·미착용은 실제 그림이 있는 조합을 사용합니다. 관계 단계명·취향·반응 대사·사건·엔딩은 미확정입니다.

아래의 새 파일은 예정 이름입니다. 파일 생성 자체를 구현 완료로 취급하지 않습니다.

기존 전역 객체 경계를 당장 모두 재작성하지 않고, 기능이 커지는 부분만 분리합니다.

## A. 출발과 중간 저장 구조 — P0

**해결할 문제:** 현재 dateWithOutfit은 출발부터 결과까지 즉시 완료합니다.

상태 후보:

- activeDate: 데이트 정의 ID, 실행 ID, 콘텐츠 버전, 현재 단계, 이미 선택한 항목, 출발 당시 코디, 지출 기록.
- knownFacts: 플레이로 알게 된 정보 ID와 출처 이벤트 ID.
- eventFlags: 주요 완료 사실. 최근 활동 200건이 잘려도 해금 조건을 유지.
- eventQueue: 실행 가능한 사건 ID. 표시 순서와 중복 방지.
- relationshipStage: 공동 기획에서 정할 관계 단계 ID.
- outfitPresets: 소유한 의상·소품 조합의 즐겨찾기.

실행 ID는 중복 거래를 구별하는 식별자이며 기기 밖으로 전송하지 않습니다. DOM 노드, 이미지 객체, 함수는 저장하지 않습니다.

**완료 기준**

1. 버전 2 저장을 잔액·소유 의상·추억 손실 없이 새 구조로 업그레이드.
2. 시작·선택·완료가 검증을 통과한 단일 상태 전이로만 적용됨.
3. 현재 단계에 없는 선택, 재전송된 선택, 완료된 실행 ID를 거부.
4. 진행 중에는 다른 일·데이트·날짜 이동이 충돌하지 않게 UI와 엔진 양쪽에서 제한.
5. 확인 후 중단 규칙을 구현하고, 출발 전 취소와 출발 후 중단을 구분.
6. 저장을 덮어쓰기 전에 검증. 자동 저장 실패 시 기존 백업 안내 유지.
7. 향후 콘텐츠 수정으로 진행 단계가 사라질 경우 무조건 초기화하지 않고 복구 경로 제공.

## B. 카페 한 코스의 선택 구조 — P1

**데이터 형태 후보**

```text
dateDefinition:
  id, contentVersion, placeId, entryConditions
  cost, timeCost, energyCost, firstNodeId
  nodes[]:
    id, approvedTextKey, backgroundKey, expressionKey
    choices[]:
      id, labelKey, conditions, effects, nextNodeId
```

구조 예시이며 실제 수련 대사나 특정 사건의 승인이 아닙니다. 테스트용 콘텐츠는 tests 전용 데이터로 두고 공개 플레이에 미승인 대본을 섞지 않습니다.

**행동의 처리 순서**

1. 준비 화면에서 가능 여부·자원·코디 미리보기.
2. 출발 확정 시 필요한 자원을 한 번 차감하고 activeDate 생성.
3. 선택 ID 검증 후 효과를 한 번 적용하고 다음 단계 저장.
4. 마지막 단계에서 공통 완료 보상과 기억을 한 번 기록.
5. 다음 이벤트의 조건을 확인하고 선택 가능한 만남으로 표시.

선택별 보상과 완료 보상을 구분해 같은 호감 변화가 두 번 적용되지 않도록 합니다. 미리보기는 상태를 바꾸지 않아야 합니다.

**완료 기준**

- 3개 단계, 각 2~3개 선택이라는 시험 범위 안에서 최소 두 가지 다른 결과를 재현.
- 단기 분위기와 장기 호감·신뢰가 구분됨.
- 왜 결과가 달라졌는지 시스템 피드백 제공.
- 대화 이력과 취향 노트가 저장되고 재로드 후 유지.
- 실제 공개 코스 완료에는 사용자와 정한 대사가 필요.

## C. 코디·표정 — P2

- 현재 의상 세트 + 스타킹 조합부터 즐겨찾기 3칸을 제안.
- 미보유 아이템을 즐겨찾기 착용으로 우회할 수 없게 검증.
- 의상별 표정 지원 목록을 명시하고 없는 그림은 같은 의상의 기본 표정으로 대체.
- 예를 들어 치마·검은 스타킹에서 미소 그림이 없다고 기본 후드로 바뀌면 안 됨.
- 추억의 의상·소품 ID는 현재 착용과 분리. 중요한 사건 CG는 최근 60회 목록과 별개로 영구 해금 가능.
- 신규 의상 수보다 현재 6가지 모습의 표정 3종 완비를 먼저 검토. 현재 8장 기준 추가 10장 필요.
- 그림은 현 캐릭터·체형·화풍·구도 기준으로 생성하고 실제 UI에서 확인.

**완료 기준:** 모든 지원 조합 로딩 성공, 미지원 조합의 일관된 대체, PC 해상도별 비교, 과거 추억 불변.

## D. 일정·약속·선물 — P3

**일정**

당일 만남 가능 정보부터 시작합니다. 예약 확장 시 시간 소비와 시각을 별도 모델로 분리할지 먼저 정합니다. 단순히 ap가 남았다는 사실만으로 약속 시간 준수를 판정하지 않습니다.

**약속**

예정 → 진행 → 이행 / 변경 / 취소 상태를 명시합니다. 일정 변경 규칙과 수련의 반응은 공동 기획 대상입니다. 행동 전 충돌 안내, 변경 가능 대안, 한 번만 적용되는 결과가 필요합니다.

**선물**

상점 구매 → 인벤토리 보관 → 선택 전달 → 수량 감소 → 반응·발견 정보 기록. 아직 보유하지 않은 물건, 전달 완료된 실행, 진행 중 대화와 충돌하는 전달을 거부합니다.

**완료 기준:** 예약 중 일하기, 날짜 이동, 중단, 저장 복원, 같은 선물 연속 전달, 수량 0, 잔액 부족을 모두 검증.

## E. 이야기 연동 — P4

공동 기획에서 정한 장면만 콘텐츠 목록에 등록합니다.

필요 조건은 호감·신뢰, 선행 사건, 알려진 정보, 특정 활동 이력 등입니다. 매일의 일정·계절은 달력을 사용하되, 개인 사건을 단순히 ‘7일째이므로 무조건 발생’하도록 고정하지 않는 방향을 제안합니다. 원작 프로젝트의 월간 리포트·방송·팬덤 트리거를 이 별도 게임에 자동 이식하지 않습니다.

주요 사건은 eligible → queued → active → completed로 추적합니다. 서로 충돌하는 장면, 일회성 중복, 오래된 활동 기록 삭제, 저장 후 재발견을 검사합니다.

**완료 기준:** 승인된 관계 분기와 사건의 선행 조건을 모두 검증하고, 첫 시작부터 해당 분기의 끝까지 실제 플레이. 엔딩 데이터가 없으면 전체 게임 완성으로 표시하지 않습니다.

## F. 재미·품질 평가

| 확인 질문 | 관찰할 신호 | 문제일 때 조정 |

| 수입 활동의 목적이 보이는가 | 플레이어가 다음 구매/외출 목표를 설명함 | 예산 안내·가격 간격 |
| 상대를 이해하며 선택하는가 | 직전 반응·취향을 근거로 다음 선택 | 피드백·정보 노출 |
